#+TITLE: Protocol BRISH3

This is the wire protocol of Brish's binary mode, spoken between =brish/brishmod.py= and the worker script =brish/brish3.zsh=. Legacy mode (=brish/brish2.zsh=, the default) is described at the end: its wire format is frozen, and the section says what its worker does within that format and what the format rules out.

* Terms
- *Bootstrap*: the zsh process Python starts. It loads the startup files once and forks the workers.
- *Worker*: one zsh subshell that serves requests, one at a time.
- *Request pipe*, *response pipes*: per worker, one anonymous pipe Python writes requests to, and two (stdout and stderr) the worker answers on.
- *Frame*: the bytes Python writes for one request.
- *Marker*: an in-band line a worker writes into its response pipes. Every marker starts with a NUL byte and ends with a newline.
- *Nonce*: 128 random bits in lowercase hex (32 characters), fresh for every request.

* Processes and file descriptors
Python creates three pipes per worker with =os.pipe()= and starts the bootstrap with the child ends in =pass_fds=:

#+begin_example
brish3.zsh -- BRIII...IIISH BRISH3-FDS <req>,<out>,<err> [<req>,<out>,<err> ...]
#+end_example

- Everything before =BRISH3-FDS= is left alone. The long =BRI...SH= word is the argv reservation that lets tools rewrite the process title in place.
- There is one =<req>,<out>,<err>= triple of fd numbers per worker, in order. Worker =i= (1-based) gets triple =i= and sets =$brish_server_index= to =i=.
- The bootstrap's stdin is a pipe from Python and its stdout is =/dev/null=. Its stderr is inherited, so startup errors stay visible.
- A bootstrap started without =BRISH3-FDS= (for example by an older Python that still speaks the legacy protocol) prints an error and exits with status 64 without running anything.
- Python starts the bootstrap in a session and process group of its own (=start_new_session=True=, that is =setsid=), with =BRISH_SESSION=1= in its environment; the bootstrap removes the variable before it forks the workers. Every worker and every command runs in that session, which has no controlling terminal. So no terminal signal (Ctrl-C's SIGINT, Ctrl-\'s SIGQUIT, Ctrl-Z's SIGTSTP, the SIGHUP of a closing terminal) and no signal to Python's process group reaches them, and a command that opens =/dev/tty= gets ENXIO. Legacy mode starts its bootstrap the same way.

The bootstrap forks the workers at top level, so each one inherits the options, functions and aliases the startup files left behind. It then closes every passed fd and reads its stdin until EOF. That EOF comes when Python closes the pipe in =cleanup()=, or when Python ends, however it ends: normally, by an exception, by SIGTERM or SIGKILL, or with its terminal (whose SIGHUP no longer reaches the workers, see above). The bootstrap then stops what is left, so that no command outlives Python. An idle worker exits by itself, since its request pipe has no writer any more. A worker still alive a second later runs a command (one whose reply Python abandoned, or one whose caller died): the bootstrap lists the processes below it with one =ps= run and sends SIGTERM to the worker and all of them, and SIGKILL to whatever is left a second later, as =kill()='s later steps would. Background jobs that commands left on idle workers, and processes that left the worker's tree (a double fork, as daemons do), are not touched; a busy worker's background jobs are below it, and are stopped with it. Then the bootstrap waits for its workers and exits. The waits go by the clock, since a timed wait can take several times as long as asked on a loaded machine. It reads with =read=, not =sysread=, because zsh reaps exited children while blocked in =read= but not in =sysread=, and Python's liveness check cannot tell a zombie from a live worker.

Each worker:
1. closes the other workers' fds;
2. moves its own three fds above 9 and closes the originals, so that a command's =exec 3>file= cannot clobber them, and the request fd still has exactly one reader;
3. opens its *empty-stdin pipe*, an always-EOF pipe (=exec {fd}< <(builtin true)=) that is the default stdin of every command;
4. points its own fd 0 at =/dev/null= and fds 1 and 2 at the response pipes, so stray output between requests lands where Python discards it;
5. writes =\0BRISH3-HELLO:<pid>\n= on its stdout pipe, where =<pid>= is =$sysparams[pid]= (inside a subshell, =$$= is the bootstrap's PID).

Python waits for every HELLO, with a startup timeout of 30 seconds by default (=Brish(startup_timeout=...)=), and records each worker's PID. A worker that exits before its HELLO, or no HELLO before the timeout, raises =BrishWorkerDiedException= with "not a BRISH3 worker" in the message.

* Request frame
#+begin_example
BRISH3 <nonce> <cmd_len> <stdin_len> <fork>\n<cmd bytes><stdin bytes>
#+end_example

- The header is ASCII, one line, five fields separated by single spaces.
- =<cmd_len>= and =<stdin_len>= are decimal byte counts (at most 15 digits). =<stdin_len>= may instead be =-=, which means "no stdin": the command reads =/dev/null= and no stdin bytes follow. A length of =0= means the empty-stdin pipe.
- =<fork>= is =1= to run the command in a subshell, =0= to run it in the worker itself.

The worker validates the header before doing any arithmetic with it, because zsh arithmetic performs command substitution. Anything else (a bad header, or EOF inside a payload) makes the worker exit without running anything; a frame of the legacy protocol, which is NUL-separated text, is one such case.

Payloads are read with =sysread= in chunks of at most 64 KiB, each straight into the next element of an array, and joined once in a quoted expansion. Appending to a scalar with =+== is quadratic, and unquoted expansions of large values are several times slower. The command lands in =$BRISH3_CMD= and, for compatibility, in =$cmd=. The stdin lands in =$brish_stdin=.

* Reply
For every request the worker writes, on both response pipes:

#+begin_example
\0BRISH3-START:<nonce>\n
... the command's output ...
\0BRISH3-END:<nonce>:<retcode>\n        after the command returns
\0BRISH3-END:<nonce>:<retcode>:exit\n   from the EXIT trap, when the command exits the worker
#+end_example

Markers are written with =syswrite= to the worker's private copies of the response fds. Each marker is shorter than =PIPE_BUF= (512 bytes), so it is written atomically even when background jobs share the pipe. The command itself runs with call-site redirections to those fds, so a command's =exec >file= is undone when it returns.

Python parses each stream on its own:

1. Before START, it keeps only the last =len(START)-1= bytes, so output left over from earlier requests, or written by background jobs between requests, is discarded.
2. After START, it collects the chunks and searches for the fixed prefix =\0BRISH3-END:<nonce>:=. Only the new chunk plus the last =len(prefix)-1= bytes before it are searched, so a prefix split across reads is still found. The prefix starts with NUL, so a chunk with no NUL byte in it or in those carried-over bytes is not searched at all.
3. Once the prefix is found, it waits for the newline after it and parses =<retcode>[:exit]=. Anything after the END line is dropped.

Output cannot end a reply early, fake a retcode or leak into the next reply, because it would have to contain the nonce, and the nonce is never visible to the command: in non-fork mode it lives only in the positional parameters of the worker's handler function, and in fork mode =builtin set --= clears them in the subshell. The stdout END carries the authoritative retcode.

* Execution
A non-fork command runs as the body of a function:

#+begin_src zsh
builtin eval "function tmp_block_8182782 {"$'\n'"$BRISH3_CMD"$'\n'"}" &&
  tmp_block_8182782 <stdin >&out 2>&err
#+end_src

- The function body lets the command use =return=.
- The =&&= matters: after a syntax error, the function from the previous request must not run again.
- The body goes through =eval= and not =functions[tmp_block_8182782]==, because assigning to =functions= does not unmetafy the body and so corrupts NUL and the bytes 0x83 to 0x9D.

A fork command runs as =( builtin set --; builtin eval "$BRISH3_CMD" )= with the same redirections. When the request has stdin bytes, a non-fork command reads them from a process substitution, and a fork command through a pipeline in its subshell:

#+begin_src zsh
tmp_block_8182782 < <(\brish3_write_stdin) ...
( builtin set --; brish3_write_stdin | builtin eval "$BRISH3_CMD" ) ...
#+end_src

A non-fork command gets no pipeline because under =emulate sh=, which a command can leave behind, zsh runs the last element of a pipeline in a subshell: the command would lose its state changes, its =exit= would not end the worker, and =kill()= would give 1. The process substitution keeps the command in the worker. Its body is parsed when it runs, under the command's options and aliases, so it is a single quoted word. zsh waits for the writer, as it does for a pipeline.

The writer, =brish3_write_stdin=, writes =$brish_stdin= with =syswrite=, after =exec </dev/null 2>/dev/null=. It ignores SIGPIPE and always succeeds, so a command that does not read its stdin still reports its own status under =pipefail=, and the write error goes to =/dev/null=. It also clears =__brish_trap= for itself (see Interrupts). Without stdin bytes no process is forked.

** Loop structure, and why
#+begin_src zsh
brish3_run() {  # $1 nonce, $2 fork, $3 stdin mode; no locals: user code runs in here
  BRISH3_NONCE= __brish_int= __brish_pb=
  {
    repeat 1 do        # absorbs a bare break or continue
      ...run the command as above, with __brish_trap set while it runs...
    done
  } always {
    BRISH3_RET=${__brish_int:-$?} BRISH3_NONCE=$1
    TRY_BLOCK_ERROR=0      # NOMATCH and other shell errors do not end the serve loop
    TRY_BLOCK_INTERRUPT=0  # nor does an interrupt (see Interrupts below)
    __brish_trap= __brish_trap_arg=  # the trap is idle again
    builtin unsetopt err_exit err_return
    ...restore posix_builtins and the worker's TRAPINT if needed...
    ...unfunction tmp_block_8182782...
  }
  builtin true         # a failing status must not reach the user's ZERR trap
}

while brish3_recv; do  # parses the frame, reads the payloads, writes START
  BRISH3_INREQ=1
  brish3_run "$BRISH3_NONCE" "$BRISH3_FORK" "$BRISH3_STDIN_MODE"
  ...write END on both pipes...
  BRISH3_INREQ=
done
...catch-up END if a user `break 2` left the loop with a request open...
#+end_src

- =brish3_run= is never called inside =||= or =if=, because that would disable =err_exit= for the command.
- END is written after =brish3_run= returns, never in =always=: while =exit= unwinds, =always= runs with =$?= set to 0.
- The worker's EXIT trap writes =END:<nonce>:<status>:exit= when a request is open, so =exit N= returns a normal result with retcode N. Python restarts the instance before its next use.
- =errexit=, =${x:?}= and similar fatal errors end the worker without an END. Python then returns retcode 9001 (see below).
- Header parsing, both payload reads and the START write happen in one =emulate -LR zsh= function, since every =emulate= and every function call costs tens of microseconds.

** Interrupts
SIGINT aborts the running command, the way Ctrl-C does in an interactive shell, and the worker goes on serving. Brish sends it, to the worker and its descendants, in two cases: =BrishPopen.kill()=, and one SIGINT when a =BrishPopen= is abandoned in its owner thread (dropped unclosed, or interrupted by an exception inside a read). The worker runs in a session of its own, which no terminal signal and no signal to Python's process group reaches (see Processes and file descriptors). A command can still signal workers itself: =kill -INT 0= in a command reaches every worker of its instance, and the bootstrap, which ignores it. A worker defines the trap below only when =BRISH_SESSION=1= says it is in such a session. Older Python starts the bootstrap in its own process group, where a terminal Ctrl-C reaches every worker, and does not set the variable: the worker then defines no trap and ignores SIGINT throughout, as workers always did, so a non-fork command runs on (see the legacy section's SIGINT paragraph).

- *One trap for the worker's lifetime.* Each worker defines =TRAPINT= once, from =brish/trapint.zsh=, when it starts, and keeps it. Every change of the INT trap in zsh 5.9 passes through the default disposition for a moment (the old trap is removed before the new one is installed), and a SIGINT in that moment kills the worker; workers that set and removed a trap around every command died within a few hundred signals of a SIGINT flood. What the trap does depends on variables that the worker sets around each command. The bootstrap ignores SIGINT.
- *Idle or framing* (reading a request, writing a marker, the worker's own code around the command), the trap's first command is =builtin return 0=. A trap that returns 0 changes nothing: =$?=, =break= and =return= are as they were, and the reads and writes the worker uses (=read=, =sysread=, =syswrite=) carry on after it, so a signal can never cut them short.
- *While a command runs*, from the moment its function is defined (or just before a fork command's subshell) until =always=, the worker sets =__brish_trap=. The trap then turns =xtrace= off for itself (zsh restores it when the trap returns, so a command under =set -x= sees only the line =+TRAPINT:1> unsetopt xtrace=), and:
  - in a subshell of the worker it exits with 128+signal. That is a fork command's subshell, whose status END then carries, or a command substitution or subshell inside a non-fork command. Subshells keep the trap function, so none defines its own;
  - inside a non-fork command's function (=${#funcstack[@]}= deeper than the trap, =brish3_run= and =brish3_serve=; =[@]= counts the elements under =ksh_arrays= too) it returns 128+signal, which makes zsh unwind the command as interrupted: the running external command dies of the signal, and zsh breaks out of the command's loops and functions. The =always= block sets =TRY_BLOCK_INTERRUPT=0=, which stops the unwinding there. (So a command cannot resume after the interrupt the way an interactive shell lets it, by setting =TRY_BLOCK_INTERRUPT=0= in an =always= block of its own: that block runs, and then the command ends with 130.) The status of an interrupted function return is 1, so the trap records 128+signal in =__brish_int=, and END carries that: 130 for SIGINT;
  - elsewhere it does nothing. Above the command's function an interrupt would break the serve loop itself, and while the worker waits for a fork command's subshell, zsh runs the trap only after the subshell has exited.
  The writer of a command's stdin (=brish3_write_stdin=, or =__brish2_write_stdin= in legacy mode: a child process, a non-fork command's process substitution or the left side of the pipeline in a fork command's subshell) clears =__brish_trap= for itself, so the SIGINT of =kill()=, which reaches it as it reaches every process below the worker, does not cut the stdin short: the command decides whether it is interrupted. It writes with =syswrite=, which goes on after a SIGINT that the trap ignores, where =print= can give up in the middle of a write. (A legacy worker without =zsh/system= writes with =print=, but it has no trap and ignores SIGINT.) The trap assigns with =typeset -g=, which =warn_nested_var= does not report.
- Some options make zsh exit instead of unwinding, and a command may have set them. Under =err_exit= (=set -e=) the interrupted command's non-zero status exits the shell, and so does =err_return= at the legacy worker's top level, where it acts as =err_exit=. Under =posix_builtins= (part of =emulate sh= and =emulate ksh=) an interrupt that lands inside a special builtin such as =eval= or =.= is fatal to a non-interactive shell. So the trap turns =err_exit=, =err_return= and =posix_builtins= off before it returns, and =local_options= as well: the trap inherits =local_options= from where it runs, and its own return would otherwise undo these changes. Whenever the trap turned =posix_builtins= off, the =always= block sets it back to what it was before the command (the trap cannot tell a global setting from one that a scope undoes as the interrupt unwinds out of it, and a worker left with =posix_builtins= on would die of the next failing special builtin); it turns the other two off after every command anyway.
- *Cases that cost the worker.* A scope that restores options when it returns (a function with =setopt local_options= or =emulate -L=, and =emulate -c=) turns the options back on as the interrupt unwinds out of it, and the restored option then exits the worker:
  - =err_exit= (in legacy mode also =err_return=) set outside the scope meets the scope's non-zero status, as in =set -e; f() { emulate -L zsh; sleep 100 }; f= or =set -e; emulate zsh -c 'sleep 100'=;
  - =posix_builtins= set outside the scope comes back while the unwinding is still inside a special builtin, as in =emulate sh; f() { setopt local_options; sleep 100 }; eval f= or =emulate sh; eval 'emulate zsh -c "sleep 100"'=.
  So does any SIGINT while a non-fork command has removed the trap (=trap - INT=, =unfunction TRAPINT=): the signal then has its default disposition, which kills the worker. Python reports retcode 9001 for each and restarts the instance. In a fork command only the subshell dies (130).
- A command may set its own INT trap (=trap 'print caught' INT=, or its own =TRAPINT= function), which then runs instead, as in an interactive shell. It lasts until the command ends: the worker notes which file its own trap came from (=$functions_source[TRAPINT]=, right after it sourced =trapint.zsh=; with zsh before 5.4, which lacks =$functions_source=, the trap's body), and =always= sources the file again when the current trap differs. Such a change passes through the default disposition too, at the command's own change and again at its end. A command's own trap does not record 128+signal: when it unwinds a non-fork command (a =TRAPINT= that returns non-zero), the retcode is 1, the status of an interrupted function, and a trap string's =return 7= gives 7. A command that ignores SIGINT (=trap '' INT=) and loops in the shell cannot be interrupted: =kill()= then escalates to SIGTERM and SIGKILL (see the readme, "Streaming output").
- zsh runs a trap only once the foreground child has exited (unless =trapsasync= is on), which is why =kill()= signals the descendants as well as the worker. It signals the worker first: its trap then runs as the child dies of the signal. The other way round, a kill thread held up between the two (by the GIL or the OS) let the worker reap the child and go on before its own SIGINT arrived, so the command ran on, or under =set -e= the child's 130 exited the worker. Step 2 sends its SIGINT to the worker before its SIGTERM to the descendants for the same reason.
- Step 4 SIGKILLs the worker, so Python first makes sure that the command has not ended: before step 4, and at step 3 when no process runs below the worker, it reads what the pipes already hold (up to 128 KiB beyond its read-ahead, for at most half a second) and looks for the end of the reply, which can wait there behind output that the caller has not read. A fork command with no process below the worker has exited, and the worker has only END left to write, so step 4 then comes a grace later, and only if END has not arrived by then.
- *zsh can crash or hang in a trap.* zsh 5.9 runs a trap from its signal handler, unless it is waiting for a child, so the trap runs in the middle of whatever the signal interrupted. The trap allocates memory: when the signal lands inside a =free()= of zsh's (most are not guarded), the allocator's lock is already held, and the worker crashes (macOS: SIGTRAP, exit status 133). The worker keeps such frees out of its own code between commands where it can: it removes the command's function with =unfunction=, which holds signals back, instead of letting the next definition free it. A command's own shell code can still be hit, for example while it defines a function. That is rare for a single SIGINT, but a flood of them (hundreds per second) can kill a worker that runs such code; Python then reports 9001 and restarts the instance. =kill()= sends at most two SIGINTs per command (steps 1 and 2), so only a program that signals the worker itself can flood it. =test_g8_sigint_flood_between_commands= floods a worker that runs =print= back to back.
  zsh also flushes stdout after every builtin, the trap's own included, and the trap cannot do without builtins: only =return= (or =exit=) makes zsh unwind the command. When the signal lands while a builtin of the command (=print=, =echo=) is inside the C library's lock or unlock of stdout, that flush waits for the lock forever, and the worker hangs. Python cannot tell this from a long command. =kill()= ends it at step 4 (9001, and a restart); a fork command's subshell hangs the same way, and the SIGTERM of step 2 ends it (143). It is rare: floods of SIGINTs (about 150 per second for 15 s) at a worker that ran =print= back to back hung it in 3 of 72 runs, about once in 50,000 signals, and the macOS sampler showed the trap's flush waiting in =flockfile= inside a =print= that the signal had interrupted in =funlockfile=. The trap's code cannot avoid it. The same interplay can make the interrupted =print= write its line a second time before the command ends with 130: one command in about 125 such floods did.

Older Python, such as master's binary mode (6e97135), reads such a reply like any other: the retcode is 130. =tests/test_binary_compat.py= runs master's Python against this worker.

** Defences against user state
User commands run in the worker, so they can change its state. The worker is written to survive that:
- Aliases are off while =brish3.zsh= is parsed (startup files may define global aliases), and turned back on before the first command, if they were on, so commands keep their aliases.
- Every internal command is prefixed with =builtin=, so user functions named =print=, =read=, =eval=, =sysread=, =syswrite= or =true= are never called.
- Internal names use the =BRISH3_*= and =__brish3_*= prefixes. None is read-only, because assigning a read-only variable is fatal in zsh.
- Internal logic runs in =emulate -LR zsh= helpers. The code between them only expands scalars inside double quotes, and the marker prefixes (which contain NUL) are computed once at startup, so =ksh_arrays=, =sh_word_split=, =no_multibyte=, =nounset=, =posix_strings= (from =emulate sh=) and a changed =IFS= do not break the loop.
- =err_exit= and =err_return= are cleared after every request.

A command that deliberately reads or overwrites the worker's internals (its fd variables, say) can still break it. That is outside the guarantee.

* Python side
- One =selectors.DefaultSelector= per worker watches both response pipes.
- The whole frame is built before anything is written, so an encoding error leaves the worker untouched.
- The frame is written non-blocking inside the same select loop that drains the response pipes. A readable pipe is read until a read comes back short before the next select. A blocking write deadlocks when the worker is still busy with an earlier, abandoned command that fills its output pipe.
- *Worker death* is any of: EOF on a response pipe, =EPIPE= on the request pipe, or the worker's PID gone when the pipes have been silent for 0.5 s (a background job can hold the pipes open after the worker dies). On death, Python first collects whatever the worker already wrote, then:
  - if START was seen, the command ran: the result carries the END retcode if one arrived, and otherwise retcode 9001 with =brish: worker died during this command= appended to stderr. The instance restarts before its next use;
  - if START was not seen, the command never ran: Python restarts the instance and retries once, and raises =BrishWorkerDiedException= if the retry fails too.
- *Interrupts.* An exception (such as =KeyboardInterrupt=) once the whole frame is written, while waiting for START or reading the reply, leaves the worker *stale*: the command keeps running, and the next request on that worker skips the old reply through its own START. (A =BrishPopen= also sends the command one SIGINT when an exception ends one of its reads; =send_cmd=, and =popen= before it returns, do not.) An exception while the frame is being written leaves the worker *broken*: it may hold part of a frame, and would read the next request as the rest of it, so the next request could run as code inside the old command. A broken worker takes no request again: a call on it counts as one that never ran, and the instance restarts before its next use. A thread that holds a worker lock cannot restart, so its calls on that worker raise =BrishWorkerDiedException= until it has released its locks. =acquire_lock= with =server_index=None= tries idle workers first, then stale ones, then broken ones.
- *Restarts* never happen in a thread that holds a worker lock, of any worker (locks are owned per thread: =RLock= ownership). =restart()= takes the instance lock and then waits for every worker lock, so a lock holder that waited for a restart, or for the instance lock, would deadlock with it. Such a thread only schedules a restart (=restart()= returns =False=, and =%BRISH_RESTART= answers "Restart scheduled"); it runs at the next use by a thread that holds no worker lock, after every in-flight command has released its lock. A lock holder also skips the instance lock in =acquire_lock=, which is safe because the instance cannot be replaced while it holds a lock of the current generation. A call that finds its worker dead (or, in legacy mode, still busy with an abandoned reply; in binary mode, holding part of a request frame that an interrupt cut short) while the thread holds a lock raises =BrishWorkerDiedException= at once instead of waiting. A thread may hold several worker locks: a restart takes them without ever blocking on one while holding another. A generation counter makes several threads that notice the same death restart the instance only once. One worker's death recycles every worker of the instance. A =BrishPopen= holds its worker lock until its output has been read to the end, so an endless stream (=tail -f=) holds up a due restart, and with it every call from a thread that holds no worker lock, until the stream ends or is killed. =cleanup()= also takes every worker lock first, so it waits for every =send_cmd= and =BrishPopen= in flight, except a =BrishPopen= that was collected in another thread than its owner (an orphan) once a helper thread has read its reply to the end: its worker is idle, but only the owner can release the lock, at its next call. =cleanup()= skips such a lock when nothing else holds it: the owner thread has ended, or the orphan's level is the only one the owner holds on that lock (Python's =RLock= shows its count only in its =repr=, which Brish reads; when it cannot, it waits). It polls the locks it waits for, since a lock can become skippable meanwhile; then it sends SIGTERM to the HELLO PIDs, and SIGKILL after one second, so it never waits for a command that its caller gave up (one still running on a stale worker). A worker that may still run a command (a stale or broken one, or one that a =BrishPopen= of the calling thread holds) gets these signals together with every process below it (one =ps= run), so that its command does not outlive the instance either; legacy mode's =cleanup()= does the same for a worker whose reply was abandoned, with the PIDs from the bootstrap's report (without them, for every worker).
- *Streaming* (=Brish.popen=) uses the same parser, fed chunk by chunk: each chunk's certain payload is passed on at once. The only bytes held back are a suffix that starts at a NUL and could be the start of the END prefix, so output without NUL is never delayed. The reader takes one read per ready pipe and hands the chunks out before it reads again, so a caller that stops reading leaves the pipes full and the command blocked. Once =kill()= has sent its first signal, the reader reads up to 256 KiB ahead of the caller, merging each new chunk into the last one it holds of the same stream once 4 are waiting (up to 64 KiB): at each of the caller's reads it takes what the pipes already hold, and when a kill step is due, it first reads for as long as the command keeps writing (until the pipes have been quiet for 0.1 s, at most 0.5 s). So it sees the end of the reply even when the caller reads slowly (see the readme, "Streaming output"). Legacy mode's =BrishPopen= reads each reply FIFO in a thread of its own, with the same parser as =send_cmd=; the two threads put their chunks on one queue of at most 64 KiB for both streams (once 4 chunks are queued, a chunk joins the last queued one of its stream, up to 64 KiB), and only a full queue makes them wait. After =kill()='s first signal the queue takes 256 KiB more.

* Why anonymous pipes
The legacy transport uses named FIFOs. Binary mode uses anonymous pipes passed with =pass_fds= because:
- on macOS, kqueue and poll miss readiness on FIFOs and never report FIFO EOF, which rules out a select loop;
- opening FIFOs has an ordering constraint (each open blocks until the other side opens), which hangs =init()= when a worker dies before opening its end;
- a macOS FIFO holds only 8 KiB, while an anonymous pipe holds 64 KiB;
- nothing touches the filesystem, and there are no paths to clean up.

* Contract for a custom =shell==
=Brish(binary=True, shell=[...])= runs the given argv with =BRISH3-FDS= and the fd triples appended. A replacement worker must:
- find the last =BRISH3-FDS= argument and serve one worker per triple after it, closing the fds it does not use (otherwise Python sees no EOF when a worker dies);
- write =\0BRISH3-HELLO:<pid>\n= on each stdout pipe before the startup timeout, with the PID of the process that serves that worker;
- parse frames and write START and END markers exactly as above, each marker in a single write shorter than =PIPE_BUF=, on both response pipes;
- exit when its stdin (the bootstrap's) reaches EOF, or at least not hold the pipes open forever, and stop the commands it still runs then, if no command is to outlive Python.
- expect to run in a session of its own, without a controlling terminal, with =BRISH_SESSION=1= in its environment.

* Legacy mode
=brish2.zsh= is the worker of legacy mode. Its wire format is *frozen*: Python processes that still run older Brish code (the pre-binary release, in a long-lived server or an IPython kernel, say) spawn the on-disk =brish2.zsh= by path on every =init()= and =restart()=, so whatever worker is on disk must answer them exactly as the original did. =tests/test_wire_compat.py= checks this. It loads the old =brishmod.py= sources from git, with =__file__= pointing into the tree so that they spawn today's worker, runs a corpus through them and through a raw FIFO driver, and compares every reply byte for byte with the original worker's, both with an empty =ZDOTDIR= and with the real startup files. The intended differences (the error handling below) are asserted separately.

Two more differences show up only with unusual user state, and are not in the corpus:
- A DEBUG trap that a command sets also fires on the worker's own commands until it is removed, in both workers. Today's worker runs more internal commands per request, so such a trap prints more often.
- The original worker left a global =ret= holding the previous command's status. Today's worker keeps its state in private =__brish2_*= variables, so a command that reads =$ret= without setting it finds it unset.

** Wire format
- *Bootstrap.* Python creates three FIFOs per worker (request, stdout, stderr) and writes to the bootstrap's stdin: the request FIFO paths, NUL, the stdout FIFO paths, NUL, the stderr FIFO paths, NUL, and a newline. Each list is newline-separated. Every Python, old and new, then keeps that stdin open until =cleanup()= or its own end, and today's bootstrap reads it until EOF and then stops what is left, as in binary mode (see Processes and file descriptors). Today's bootstrap writes its workers' PIDs on its stdout (see Execution below), which older Python never reads.
- *Request*, on the request FIFO: =cmd NUL stdin NUL fork NUL newline=, where =fork= is =y= or empty. The newline is what Python's =print()= added in the original code. The worker reads it as a leading newline of the next command, where it is harmless, so today's Python still writes it. Every Python writes all three fields of a request. One that ends before its last NUL (the FIFO's writer closed in the middle of it, as Python's end does while it writes a large stdin) is not run: the worker exits, as a binary worker does on EOF inside a payload. Earlier workers ran such a command on the part of its stdin that had arrived, after its caller was gone.
- *Reply*, on the stdout FIFO: the command's output, =\n NUL \n=, the decimal retcode and a newline. On the stderr FIFO: the output, then =\n NUL \n=.
- Python reads each FIFO until the first line equal to =NUL \n=, and drops the one newline the worker wrote before it. Older Python reads line by line; today's Python reads bytes (lines end at =\n= only) with a parser that searches the buffered bytes for =\n NUL \n= (or =NUL \n= at the very start), gives the same split, and consumes nothing past the reply. =send_cmd= and =popen= share that parser; streaming holds back only a trailing =\n= or =\n NUL=, which could be the start of the delimiter. stderr is read in a helper thread, so a command that fills the stderr FIFO before finishing its stdout cannot deadlock.

Two kinds of retcode line are newer than the original worker, and both parse as integers in old Python:
- =+N=, from the worker's EXIT trap: the command exited the worker with status N (=int("+3")= is 3);
- =09001=, written by the bootstrap for a worker that died without answering. It parses as 9001 everywhere, and the leading zero tells it apart from a command's own =return 9001=, which zsh prints as =9001= (function statuses can exceed 255). Today's Python treats only =09001= as a death.

** Execution
The bootstrap forks one subshell per worker after the startup files have run, with fd 0 on the request FIFO and fds 1 and 2 appending to the reply FIFOs. A non-fork command runs as the body of =tmp_block_8182782=, and a fork command in a subshell, as in binary mode (see Execution above): =eval= defines the function, =&&= keeps a syntax error from re-running the previous body, and the same =repeat 1= / =always= construct absorbs =break=, =continue=, NOMATCH and other shell errors, and clears =err_exit= and =err_return=. The reply is written at the top of the read loop, so a command's =continue 2= still gets one, and an outer loop absorbs =break 2=.

stdin works as in binary mode: an empty stdin is an always-EOF pipe opened once per worker, so a command without stdin forks nothing, and a non-empty stdin comes from =__brish2_write_stdin=, which ignores SIGPIPE and always succeeds: a process substitution for a non-fork command, and a pipeline in a fork command's subshell. The writer replaces its stdin with =/dev/null= by =exec=, since a redirection of a group would keep a saved copy of the worker's fd 0, the request FIFO, open while it writes. The worker's fd 0 is the request FIFO, and no command may inherit it: it would eat the next request, and a background job holding it would keep a dead worker's FIFO open. Every command therefore gets its stdin from a call-site redirection, so zsh moves the request FIFO to an internal fd while the command runs, and closes that fd in every child. A test checks every fd of processes that commands start, in each shape (plain, background, subshell, command and process substitution, pipeline).

The defences against user state follow binary mode's: the script is parsed with aliases off, every internal command is prefixed with =builtin=, framing uses private constants computed once at startup (a =$'\0'= literal evaluates to the empty string while a command's =posix_strings= is on), and =>&1 2>&2= at the call site undoes a command's =exec >file=. =$MARKER= is still defined, for commands that read it, but nothing depends on it. One quirk needs its own fix: zsh skips an EXIT trap that was set while =posix_traps= was off if a command later turns it on (=emulate sh= does) and then exits from inside a function. So the worker sets its EXIT trap again before every request.

Python starts the bootstrap in a session of its own with =BRISH_SESSION=1=, as in binary mode, and SIGINT is then handled as in binary mode (see Interrupts above), with the same =TRAPINT= from =trapint.zsh=, defined once per worker: it returns 0 while the worker is idle or framing, records 128+signal while a non-fork command runs (acting only inside =tmp_block_8182782=, since an interrupt at the worker's top level would break its read loop and end it), exits with 128+signal in a subshell, and =always= sets =TRY_BLOCK_INTERRUPT=0=. The worker writes its replies with =syswrite= (only that builtin is loaded from =zsh/system=), which carries on after a trap that returned 0, where =print= gives up its write. A worker whose zsh cannot load =syswrite=, or cannot read =trapint.zsh=, ignores SIGINT instead (=trap '' INT=), as workers did before, except while a command's own INT trap lasts. Neither that state nor a command's trap string is a function, so the worker cannot tell them apart, and it sets =trap '' INT= again after every command, a change that, like every change of the INT trap, passes through the default disposition for a moment. The retcode line is then a plain =130=, and the worker lives on; =test_sigint_aborts_only_the_command= checks this. Older Python (the pre-binary release, master) starts the bootstrap in its own process group without =BRISH_SESSION=, and the worker then defines no trap and ignores SIGINT throughout, as the original worker did: workers start as background jobs of a non-interactive zsh, which ignore it. A SIGINT to the worker and its processes, a terminal Ctrl-C included, then leaves a non-fork command running to its end, external programs included, while a fork command's subshell dies of it (status 130); the worker survives either way. =test_sigint_under_old_python= checks that this worker answers such SIGINTs exactly as the original does, under both older Pythons. =BrishPopen.kill()= needs each legacy worker's PID. Once it has forked the workers, the bootstrap writes =NUL BRISH2-PIDS:<pid> <pid> ... newline= (one PID per worker, in order) on its stdout, which nothing else writes after the startup files and which older Python never reads. The first =popen= of a generation reads it, waiting up to 5 seconds, and takes each PID that is in the bootstrap's process group (the session Python started). A shell that is not called =brish2.zsh=, or did not report within that time, gets one internal request per worker and generation instead: =print -r -- "$(zmodload zsh/system && print -r -- brish-pid:${sysparams[ppid]}:)"=, the parent of a command substitution, so that the worker itself loads only =syswrite= from =zsh/system=. The marker and the PID are printed together, inside a quoted substitution, so that worker state (a DEBUG trap that prints, digits in =IFS=) cannot split them. The marker lets Python find the PID in a reply that a background job's output has joined (see "What the frozen format rules out" below); the last match is used, and only if =ps -o ppid= -p PID= names the instance's bootstrap as its parent.

** Worker death
- *=exit=* in a non-fork command runs the EXIT trap, which writes =\n NUL \n +N \n= on stdout. A helper process writes the stderr delimiter once the worker has fully exited (its parent PID changes then), so by the time Python has the whole reply, the request FIFO has no reader. The next write then fails with =EPIPE=: today's and master's Python restart and retry, and the pre-binary Python raises =BrokenPipeError= (with the original worker, it spun on EOF forever). Today's Python reads the =+= and restarts before its next use, without trying the dead worker first.
- *=errexit=, =${x:?}=, signals* end the worker without running EXIT traps. The bootstrap records each worker's PID, and on every CHLD it checks them all with =kill -0=. For each worker that is gone, and only for those, it opens that worker's reply FIFOs without blocking and, if a reader is there, writes =\n NUL \n 09001 \n= and =\n NUL \n=, once. So the caller gets retcode 9001 even while a background job holds the reply FIFOs open (no EOF can arrive then), and old Python gets a reply instead of spinning on EOF. The other workers' FIFOs are left alone, so their busy commands and later replies are their own (=test_a_dying_worker_leaves_the_others_alone= kills one of three workers under each Python). If the dead worker had already answered, or was idle, nobody reads those bytes: the next request to it finds the request FIFO without a reader, and the instance restarts with new FIFOs (the pre-binary Python raises =BrokenPipeError= instead, as it did with the original worker).
- Today's Python appends =brish: worker died during this command= to stderr for =09001=, and also returns 9001 on EOF of a reply FIFO.

** What the frozen format rules out
Each of these would need a change the old Python cannot parse. Binary mode has none of them.
- *A NUL cannot travel in a command or its stdin.* The fields are NUL-terminated. Such a request returns retcode 9000 without touching a worker. A NUL inside an interpolated value works, because the quoter writes it as =$'\x00'=.
- *An output line that is only a NUL ends the reply early.* That includes output that is just a NUL, or ends in =\n NUL=, on stdout or stderr. The delimiter carries no nonce, and old Python must keep recognising it. The rest of the output is then read as the next reply, so results lag one behind, or, when the line after the forged delimiter is not a number, =send_cmd= raises =ValueError= and the instance restarts. A NUL anywhere else in a line is carried exactly.
- *Output written between requests* (by a background job) joins the next reply, since there is no START marker to skip it.
- *Large stdin is slow.* The worker reads requests with =read -d=, which makes one syscall per byte on a FIFO: about 1.5 seconds per MiB. A buffered =sysread= reader would fit the format, since only the worker reads the request FIFO, but is not done yet.
- *=cmd_stdin=None= is an empty stdin*, not =/dev/null=: the wire has no way to say "no stdin".
- *An interrupt restarts the instance.* Without a per-request marker a worker cannot be resynchronised. This is about =KeyboardInterrupt= in Python, which abandons a reply half-read (or a request half-written), also the internal PID request's; =BrishPopen.kill()= interrupts the command and reads its reply to the end, so the worker keeps its state, and so does a =BrishPopen= that is dropped unclosed after its reader threads have read the whole reply. Until the restart, the abandoned worker takes no request, also not from a thread that holds its lock: that call raises =BrishWorkerDiedException=.
